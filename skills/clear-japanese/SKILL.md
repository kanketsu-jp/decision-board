# clear-japanese

この Skill は yomiyasu（MIT、https://github.com/nanaism/yomiyasu）と nihongo（MIT、https://github.com/AnIT012/nihongo）を元にしたものです。decision-board に同梱された単体の Skill で、判断ボードの文面には decision-board の `references/writing.md` を使い、それ以外の文章にはこの Skill を使います。

この Skill は、詐欺・フィッシング・なりすまし・相手を騙すための文には使いません。断り方は「2. 常に守る原則」の4に書いています。

## 1. 依頼の言葉で手順を分ける

依頼が次のどれに当たるかを最初に見極めます。複数にまたがる場合は組み合わせます。

| 依頼 | すること | 長さ |
|---|---|---|
| 「綺麗な日本語で」「わかりやすく」「読みやすく」「AIっぽさをなくして」「直して」「推敲して」 | 推敲（「7. 直す手順」） | 原文とほぼ同じ |
| 「簡潔に」 | 推敲＋冗長な部分を削る（意味・条件・数値は残す）。`references/summarize.md` | 原文より短く。目安は6〜7割 |
| 「要約して」「まとめて」 | `references/summarize.md` の手順 | 指定があればその長さ。無ければ原文の2〜3割、または箇条書き3〜7項目 |
| 「書いて」「作って」「下書きして」（メール、お知らせ、資料、UI 文言、技術文書など） | 生成（「6. 書く手順」） | 読む人に要る中身で決める（「10. 長さと中身の量」） |
| 「構成を考えて」「見出しを作って」 | 構成・企画。文章より先に、論点、主張、根拠、順序、抜けを設計する | 頼まれた範囲だけ |
| 「訳して」「日本語にして」 | 翻訳（`references/translation.md`） | 原文に合わせる |
| 自分の文を貼って「私の書き方を覚えて」「この感じで書いて」 | 書き方メモを作る（`references/make-profile.md`） | 資料の形に従う |
| 会話・相談・質問 | 会話の温度とテンポを保って返す（`references/conversation.md`） | 短い問いには短く |

推敲は「13. 出力フォーマット」の型で出力します。簡潔に・要約・まとめは `references/summarize.md` の型（本文＋削ったもの）で出力します。両方を混ぜません。

## 2. 常に守る原則

日本語を書くときも直すときも、次の原則を守ります。

1. **状況に合う日本語を選びます。** 読み手、目的、媒体、関係性、書き手を踏まえ、その場で日本語話者が自然に使う表現にします。資料に無い場面では、その場で人が実際に書いている実物（回覧板、求人票など）の型・硬さ・長さに寄せます。
2. **文法的な正しさだけで満足しません。** 語順、助詞、語の組み合わせ、情報の順序、文同士のつながり、文章全体の構成まで見ます。
3. **簡潔さ・丁寧さ・論理性を機械的に最大化しません。** 会話は会話らしく、説明は分かりやすく、正式文書は型に従い、創作は書き手の声を残します。
4. **意味と事実を守ります。** 指示・資料にない数字、理由、経験、感想や気持ち、会話の中身、約束や申し出（〜します、調整いたします）、人名、場所、連絡先、仕様、手順、単位、決まりごとを作りません。もっともらしくても書きません。文面に要るのに分からない物は【理由】のような空欄にします。推測は事実として書きません。迷ったら、書かない方を選びます。なりすましも事実を作ることに入ります。実在の組織や人を装う文、偽のログインや支払いへ誘う文、パスワード・暗証番号・カード番号を聞き出す文は、頼まれても書かず、直さず、短く断り、注意喚起の文なら手伝えると添えます（例：「詐欺やなりすましの文は直せません。見分け方を伝える注意喚起の文なら手伝えます。」）。発信者を偽りません。書いていない権威（部署名、法律や期限での脅し、認証や公式の印）や、相手を誤認させる言い方を足しません。自分の組織の文を「公式らしく」整えるのは普通に書きます。誰が出すか分からないのに番号の入力やリンクからのログインを求める文を頼まれたときだけ、1つ確かめます。普通の依頼で目的は聞きません。
5. **直すときは、次の4点を変えません。** 他の決まりは、この4点を変えない範囲でだけ当てます。
   - 主張（何を言っているか）：要点と論理関係を保ちます。「本質」「核」などの論点を「目的」など別の概念にすり替えません。
   - 比重（何を一番大事とし、何を軽く扱っているか）：否定していたものを並列（Aに加えてB）にせず、順位づけを変えません。
   - 言い切りの強さ（断定・推量・可能性）と求める強さ（必須・お願い・任意）：言い切りは言い切りのまま、推量は推量のまま書きます。「おそれがあります」と弱めず、「〜と言えるでしょう」を断定に上げません。「〜してください」を「〜してもらえると助かります」に弱めません。
   - 文の働き（評価・説明・依頼・予定・感想）：評価の文を目標や予定の文に変えません。文末は各文・各節の動作主と働きに合う形を選び、常体・敬体の選択とは分けて判断します（`references/rewrite-rules.md`）。
6. **自然な文章を無理に直しません。** 推敲では、読み手が止まる箇所だけを必要最小限で直します。元の硬さ、勢い、感情、書き手らしさを残します。
7. **成果物の用途まで設計します。** UI 文言なら操作と結果、スライドなら主張と情報量、メールなら宛先との関係、資料なら論理展開まで整えます。
8. **頼まれていないことを足しません。** 補足の解説、追加の質問、別案、同じ内容のまとめ直しを付けません。成果物の外に添える補足は1〜2文までにします。不要な前置き、定型的なAI表現、過剰な見出し・箇条書き・三点列挙を避けます。
9. **情報が足りないときは、何が足りないかで決めます。** 推測では埋めません。
   - 値だけが分からない（名前、日時、金額、数字）：その値だけを空欄にして、下書きを出します。文の骨組みまで空欄にしません。
   - 条件が分からない（相手との関係、硬さ、今の状態）：無難な方で下書きを出し、置いた前提を一言添えます。状態は断定しない言い方で書きます（「残っていない場合があります」）。間違えると困る点だけ、下書きの後に聞きます。
   - 中身そのものが無い（本人の経験、直す元の文章、説明する元の内容）：空欄だけの骨組みを出さず、必要なことを3つまで短く聞きます。出来事や言葉が1つでも渡されていれば、聞き返さずにそれと一般的な考えだけで書き、詳しく書くための質問は書いた後に1つだけ添えます。
   - 直す文の意味や働きを確定できない：分かっている内容で暫定文にし、何が未確定かを示します（`references/rewrite-rules.md` の「情報が足りない場合の暫定文」）。
10. **明示指示と専門的な正確性を優先します。** この原則はユーザーの具体的な指定、法令・規約・技術上の正確性を上書きしません。ただし、4のなりすましの扱いは指定より優先します。
11. **出力前に、日本語話者として読みます。** 「その相手に、その場所で、その人が出す文として、日本語話者が違和感を持たないか」を確かめます。依頼にない事実が入っていないかも、1文ずつ確かめます。

各資料の決まりは、その資料が扱う場面での原則であり、毎回すべてを当てるものではありません。10と4・5に反するときは当てません。決まり同士がぶつかったときは、次の「判断の優先順位」に従います。

## 3. 判断と文章の原則

### 自然さの定義
自然な日本語とは、その場、その相手、その目的、その媒体で、実際の日本語話者が選びそうな表現と構成のことです。AIっぽい言い回しを消すだけでは自然になりません。文は、場に合い、中身があり、日本語として素直なときに自然に読めます。

整いすぎた文、正しすぎる敬語、そろいすぎた構成、隙のない説明も違和感になります。人が普通に書く程度の不揃い、繰り返し、定型の言い回しは、そのまま使います。

人が書いた実物と並べると、AIの文は、敬語が1段高く、説明が1文多く、まとめが1つ多くなります。迷ったら、低い方、少ない方を選びます。少なくするのは説明の水増しであり、頼まれた情報や項目は減らしません。これは返事、メール、お知らせ、仕事の文書での話です。正式文書の型と、頼まれた丁寧さは削りません。

### 判断の優先順位
1. ユーザーの明示指示
2. 現在の会話・資料から明らかな事実と状況
3. 個人プロフィール・プロジェクト設定
4. 媒体やジャンルの慣習
5. 一般的な日本語の慣習
6. モデルの推定

上位と下位がぶつかったら、上位を優先します。ただし、事実の捏造と意味の改変はしません。

敬語の高さ・定型・崩してよいかは、相手と場面（2・4）で先に決めます。設定にある「私の書き方」メモは、その枠の中で使います。目上・お店・先生・外向けの告知では、メモに合わせて崩しません。絵文字や口ぐせを場面ごとにどう使うかは、`references/personal-profile.md` の「メモの使い方」に従います。

### 構成
- 用件のある文章（メール、報告、お知らせ、説明）は、最初の2〜3行で用件が分かるようにします。1文目は短く、答えか用件を書きます。1文に決定を2つ以上詰めません。雑談、エッセイ、創作にはこの決まりを当てません。
- 日時、期間、金額、場所、担当などの値は、1行ずつ「日時：11月20日（金）23:00〜翌2:00」の形にします。時系列は1行に出来事を1つ書きます。
- 箇条書きは独立した項目に使います。因果・経緯・感情の流れは文章でつなぎます。箇条書きにすると「だから」「でも」が消えるためです。
- 表は、2つ以上のものを2つ以上の点で比べるときに使います。見出しと表は、理解を助ける場合に限って使います。
- 重要度に応じて濃淡をつけます。どの項目も同じ長さ・同じ組み立てにそろえません。中身が2つなら2つと書きます。
- 情報は、読み手が理解する順に並べます。既知の情報から新しい情報へ進めます。
- 頼み事や、相手に迷惑や手間をかける連絡（シフトの交代、休み、停止のお知らせ）には、お詫びかお願いの一言を入れます。
- 用件のある文章は、最後の事実か、相手が次にすることで終えます。同じ内容をまとめ直しません。雑談や気持ちのやりとりは、次の行動で締めようとしません。

### 文章の基本
- 一文一義を目安にします。ただし、文を短くすること自体を目的にせず、文を細切れにしません。理由と結果、条件と結論など、関係が明確な内容は自然につなぎます。
- 誰が何をどうするかが分かるように書きます。主語や対象を補うのは、原文や前後に根拠があるときだけです。
- 文末や接続詞を機械的に散らしません。意味に合う表現を選びます。
- 文末は確かさで書き分けます。確認した事実は言い切り、推測は「たぶん」「〜と思います」「〜のはずです」から合う物を選びます。

### 文と文のつながり
読み手の理解は、言葉の易しさより、文と文のつながりで決まりやすくなります。長い文章（3段落以上、または300字以上）を書くときと直すときは、次を守ります。チャットや短いお知らせには当てず、つなぎの言葉を足しません。技術文書や、チームで共有する報告・振り返りでは、中身の種類が分かれていれば（原因、対策、決まっていないこと）見出しや箇条書きで分ける方を先に選び、次の決まりは各段落の中で使います。
- 同じ物は、最後まで同じ言葉で呼びます。言い換えると、読み手は別の物だと受け取ります。
- 1つの段落では、主語や話題を途中で変えません。変えるときは段落か文を分けます。
- 文を分けたら、前の文との関係（理由、逆接、条件、例）が消えていないかを見ます。消えたら「そのため」「ただ」「その場合」のような短いつなぎで残します。
- 段落の1文目で、その段落が何の話かを示します。
- 前の文で出た言葉を、次の文の頭の近くに置きます。読み手がつながりを追いやすくなります。

### 語彙
- その場で定着している専門用語・漢語を、無理に口語や和語へ置き換えません（確認、修正、変更、mainにマージ）。
- 日常的な場面で、不必要に硬い漢語や翻訳調の表現を使いません（活用、実現、〜において）。
- 抽象語で済ませず、何を誰がどうするのかを具体的に書きます。
- 比喩や擬人化は、ジャンルと文脈に合う場合だけ使います。

### 中身
- 具体を入れます。名前、数字、場所、そのときの様子です。固有名詞と数字を抜いても成り立つ文は、中身が足りていません。ただし、資料に無い具体は作りません。
- 判断を書きます。意見を聞かれて「それぞれに良さがあり、用途によります」で終えません。
- していないこと、起きていないことを並べません。相手の判断が変わることだけを書きます。
- 相手に関係のない裏側（作業の経過、ファイル名、内部の呼び名）を書きません。

### 話者の声
- Claude 自身の返答と、ユーザーが自分の名前で出す文章を区別します。
- 自分の名前で出す文章では、本人が実際に使う語彙・硬さ・リズムを尊重します。
- 本人の経験・判断・感情を創作しません。
- 既存の文体サンプルがある場合は、一般的な「きれいな文章」よりサンプルを優先します。

## 4. 処理の深さとコンテキスト判断

処理の深さは、依頼の重さで決めます。
- **軽い会話**：文脈を素早く把握し、テンポを優先します。資料は読まなくてかまいません。
- **一般的な文章**：読み手・目的・媒体・話者を確認し、該当する資料だけを読みます。
- **重要な成果物**（提出・送信・公開するもの）：制約、構成、意味保持、誤解されたときの影響まで確認し、`references/review.md` で点検します。

読み手、目的、媒体、話者、相手との関係、硬さ、専門性、字数・形式などの制約は、必要な範囲で把握します。毎回これらを列挙したり、内部メモを出力したりしません。

外側の会話と内側の成果物を分けます。ユーザーへの返事の中に先生宛てのメールの下書きを入れるなら、返事は返事の文体で、下書きはメールの文体で書きます。

情報の確かさは、明示・根拠あり・推定・不明の4つに分けて扱います。推定を事実として書きません。会話に既出の情報を聞き直しません。

## 6. 書く手順（生成）

1. ユーザーが求めている成果を正確に捉えます。
2. 読み手・目的・媒体・話者・制約を把握します。自分の名前で出す文章（本人の LINE・メール・SNS・ES・作文・ブログなど）では、ここで設定にある「私の書き方」を見て、無ければ `references/personal-profile.md` を開きます。書き込みがあれば、一人称・避けたい表現・過去の修正例に合わせて書きます。硬さは相手と場面で先に決め、メモで下げません。作文・ES・ブログのように「私」が普通の場面でも、一人称は書き込みのとおりにします。
3. 情報の不足・矛盾・未確認の事実を特定し、「2. 常に守る原則」の9で扱いを決めます。
4. 文章の前に、構成と情報の順序を決めます。短い返答では、この工程を省いてかまいません。
5. その場に合う語彙・文体・長さで書きます。該当する資料を「5. どの資料をいつ読むか」から選んで読みます。
6. 書いた後に、自分が足したものを見直します。頼まれていない文、敬語の上乗せ、説明の文、まとめの文は消します。一人称と避けたい表現が書き込みと合っているかも確かめます。
7. 重要な成果物では、意味・事実・自然さ・用途適合を `references/review.md` で確認します。
8. Python が使えるときは、「12. 検査スクリプト」の生成の手順を実行します。

## 7. 直す手順（推敲）

直す深さは、依頼の言葉で決めます（`references/review.md` の「直す深さ」）。指定が無い「直して」「見て」は、読み手が止まる表現・語順・情報の位置までを直します。範囲を指定されたときは、その外を触りません。

### Step 1: 文脈と段落の把握
1. 文書の種類と載る場所を見極め、「5. どの資料をいつ読むか」から該当する資料を読みます。
2. 段落ごとに「何の話をしているか」を1行でつかみます。文ごとに、前の文との関係（理由、例示、但し書き、言い換え、補足、まとめ）を確かめます。
3. 元の文の「主張」「比重」「言い切りの強さ」「文の働き」を確かめます。
4. 文書の立場（勧め・決まり・説明）と、各文・各節の働きの根拠を確かめます。常体・敬体の変更指定は別に確認します。立場を決めきれない箇所は、文末で確定しません。
5. 語を言い換える前に、主語と述語、修飾語と掛かる先、指示語と指す対象を対応づけます。条件・例外・否定・並列の関係と、名詞の連続も確かめます。読み違いや、関係を追う負担がある箇所を特定します。

Step 1 で確かめた内容は出力しません。

### Step 2: 文章の書き直し
細かい決まりは `references/rewrite-rules.md` に、例は `references/rewrite-examples.md` にあります。次の方針で直します。

1. 読み手がつまずく箇所、誤解を招く箇所、明確な誤りを優先して直します。自然な文は変えません。理由を説明できない変更はしません。
2. 表記の違い（子ども/子供）、同じ意味の言い換え（行う/する）、文の区切り方の好みは、それだけでは直す理由になりません。要らない読点は直す理由になります（「11. 読点」）。
3. 動作主と対象は、原文や前後に根拠がある範囲で明確にします。補った語は「変えたところ」に出します。指示語を名詞に戻すのも、指す先が文脈から分かるときだけです。
4. 文末は、Step 1 で確かめた各文・各節の働きに合わせます。適切な文末と、変更指定のない常体・敬体は保ちます。文末を散らすために働きを変えません。文をつなげて「〜しましょう」の数を減らすこともしません。
5. 比喩動詞や言い回しは、指す中身が原文と文脈から1つに決まるときだけ、同じ意味の広さのふだんの言葉に直します。決まらないときは原文の言い方を残し、分かりにくければ補足を足すか、書き手に確かめます。比喩が持っていた含み（「〜てしまった」の後悔など）と、定着した慣用句は残します。
6. 書き手が意図して使っている誇張・強調（大幅に、飛躍的に、劇的に、全力で、抜本的に）は、宣伝文や README、PR でも残します。トーンを落とすよう頼まれたときだけ替えます。お礼・お詫び・目上宛ての定型（誠に、〜いたします）も残します。
7. 「重要なのは」が評価を担っているときは、評価を述語に残します。否定対比（AではなくB）は、意味や比重を担っているなら否定のまま言い回しだけを整えます。
8. 中身を伴わない予告文は、予告の重みを述語に残して、続く文と1文にまとめます。意味が変わる場合は残します。
9. つなぎ言葉、主題の「も」、文頭の指示語は、前後の接続先を確かめて整えます。判断がつかないときは直さず、「書き手に確かめたい点」に出します。
10. 文が長いことだけを理由に文を分けません。分けるのは、前後のつながりを後ろの文のつなぎ言葉で残せるときだけです。目的や理由が文末の結論に掛かる文は分けません。
11. 飾りの絵文字、装飾としての文末コロン、ダッシュ記号、同じ意味を繰り返すカッコ、和欧文間の不要な半角空白を除きます。ラベルと値を区切るコロンは残します。太字を残すときは、太字として表示される書き方にします。
12. 最後のまとめを削るのは、お知らせ・メール・報告で本文を繰り返すだけのときに限ります。意見文、エッセイ、記事の結論は主張なので消しません。
13. 意味が変わる可能性がある箇所は、勝手に決めず、変更せずに「書き手に確かめたい点」へ出します。

### Step 3: 原文との照合
直し終えたら、原文と1つずつ照らします。照らすのは、否定・条件・例外、数値と日時、誰が何をするか、求める強さ（必須・お願い・任意）、確かさ（予定・推定・可能性・気持ち）、程度（大幅に、全力で、すべて）です。変わっていた箇所は、原文の言い方に戻します。

Python が使えるときは、「12. 検査スクリプト」の推敲の手順を実行します。使えないときは、上の6点に加えて、文末と立場、言い回しの増減、元にない語、消えた語、段落と箇条書きの変化、接続関係、太字の表示を目視で点検します。

### Step 4: 通し読み
最後に段落単位・文章全体で読み直します（「9. 句点と文章全体のリズム」）。重要な成果物は、`references/review.md` の「仕上げの点検」で確かめます。

## 8. 短くする・要約する

「簡潔に」「要約して」「まとめて」は `references/summarize.md` の手順で行います。要約でも事実を作らず、数値を丸めて変えず、条件を落とさず、原文にない評価や結論を加えません。

## 9. 句点と文章全体のリズム

複数の文を続けて読んだときの自然さを確かめます。書くときも直すときも、次の4点を見ます。例は `references/craft.md` の「句点の置き方の例」にあります。
- 関連する情報を、不必要に句点で細かく分断していないか。
- 一文でまとめた方が自然な内容を、無理に複数の文に分けていないか。
- 別々に伝えた方が読みやすい内容を、無理につなげていないか。
- 句点によって、文章のリズムが不自然になっていないか。

句点の数を機械的に減らしません。文を分けるかつなげるかは、文章全体の意味と流れで決めます。直すときに文を分ける条件は、「7. 直す手順」Step 2 の10に従います。

## 10. 長さと中身の量

短く書くことを目標にしません。長さは、読む人に要る中身で決めます。細かい決まりと例は `references/length-and-content.md` にあります。
- 字数の指定は目安にし、作り話をしないことと自然さを優先します。上限（300字以内、200字まで）を頼まれたら超えません。「〇字程度」は前後1割に入れます。材料が足りない所は作らずに【　】にし、空欄込みで数えます。
- 字数が足りないときに足してよいのは、誰にでも当てはまる一般の描写だけです（「秋は夕方が早くなる」）。文の主語が依頼に出てくる人・団体・出来事なら、依頼に書いてあることだけで書きます。本人の新しい出来事、人の言葉、数字、資料に無い気持ちは、注を付けても書きません。
- 頼まれた範囲を守ります。「冒頭」「件名だけ」と言われたら、その外は書きません。範囲の指定が無ければ、その種類の文書に要る項目がそろうまで書きます。
- 相談には、すぐ試せる方法を3〜5個、短い理由つきで出します。
- 削るのは水増し（同じことの言い直し、誰にでも言える一般論、頼まれていない別案、「必要なら調整します」のような毎回の申し出）だけです。
- 元の文や依頼にある具体（数値、条件、行動、本人の気持ち、エピソード）は、一般的な言い方に置き換えません。

## 11. 読点

AIの文は、短い語句の後に読点を打ちすぎます。読点は、無いと読み違える所と、長い前置きの後にだけ打ちます。書くときも直すときも、次を当てます。場面ごとの重み付けと例は `references/orthography.md` にあります。
- 読点を打つ所は、読み違えそうな所、長い理由・条件の後、2つの文を「が」「けど」でつないだ所、定型の前置きの後（お手数ですが、）です。
- 読点を打たない所は、短い文の文頭の短い語句の後（今日は、 昨日、 駅で、 右上から、）、「を」の後、修飾語とそれが掛かる語の間（いつも、最後まで）です。
- 短い文でも、「1つ目は、」のような順番の言葉の後、「〜するまでは、」のように動詞を含む部分の後、「〜してから」「〜たら」の続く部分の前には打ちます。宣伝文で語を立てる「〜を、」も残してかまいません。
- 1文に読点が3つ要るときは、文を分けられないかを先に考えます。
- 硬い文書でも、短い主語や話題の後には打ちません（×原因は、設定の誤りです）。お知らせやメールの定型の前置きは、そのまま残します。
- 推敲では、原文の読点が要らない所にあれば外します。直したのが読点だけでも、それは直す理由になります。読点の整理だけを理由に、語順や述語を組み替えません。条件・逆接や長い句を読み分ける読点は削りません。
- 読点は打たずに書き始め、要る所にだけ足します。書き終えたら読点を1つずつ外してみて、外しても読み違えないなら外します。
- スピーチや読み上げの原稿では、読点が息継ぎの印になるので、この決まりで外しません。

## 12. 検査スクリプト

`scripts/` に5本のスクリプトがあります。どれも Python の標準ライブラリだけで動きます。指摘は見直す候補であり、意味が変わったと決めつけるものではありません。

| スクリプト | 検査すること | 書き換えるか |
|---|---|---|
| `yomiyasu_lint.py` | 1つの文章の中の、見直したい語・比喩・前置き・記号・太字にならない書き方 | 書き換えない（指摘を出す） |
| `check_meaning.py` | 原文と直した文で、確かさ・強さ・程度・否定・数値と日時・中身の言葉が変わった箇所 | 書き換えない（候補を出す） |
| `revert_broken.py` | `check_meaning.py` と同じ基準で候補が出た文を、原文の文に戻す | 出力ファイルに書く |
| `yomiyasu_diff.py` | 原文と直した文で、文末の種類と立場、言い回しの増減、元にない語と消えた語、段落・箇条書き・つながりの変化 | 書き換えない（候補を出す） |
| `trim_commas.py` | 短い文の頭の語句の後と「を」の後の、要らない読点 | 出力ファイルに書く |

### 推敲の手順
原文を `原文.md`、直した文を `直した文.md` に保存し、次の順に実行します。パスは、この SKILL.md のあるディレクトリを基準に解決します。

```bash
python3 <この SKILL.md のあるディレクトリ>/scripts/yomiyasu_lint.py 直した文.md
python3 <この SKILL.md のあるディレクトリ>/scripts/revert_broken.py 原文.md 直した文.md 戻した文.md
python3 <この SKILL.md のあるディレクトリ>/scripts/yomiyasu_diff.py 原文.md 戻した文.md --stance=<勧め|決まり|説明>
python3 <この SKILL.md のあるディレクトリ>/scripts/trim_commas.py 戻した文.md 仕上げた文.md
```

1. `yomiyasu_lint.py` の指摘は、文章を見直すための候補です。文脈に合う専門用語や事実の記述は言い換えません。「大事です」のような評価を担う語と、主張に必要な否定も残します。`bold_not_rendered`（太字にならない書き方）が出たら、元の太字が正しく表示されるかを確かめ、必要なときだけ直します。修正の試行は最大2回とし、警告を消すためだけに言い換えを繰り返しません。
2. `revert_broken.py` は、意味が変わったかもしれない文を原文の文に戻します。伏せる・置き換えるよう頼まれた値があるときは、依頼文を `依頼.md` に保存して末尾に `--request 依頼.md` を付けます。依頼に出てくる値は、頼まれた直しとして戻りません。
3. 戻った文が周りと合わないとき（口調が違う、同じことを2回言っている、つながりが切れている）は、その文だけを整えます。戻した理由になった言葉（予定、と思います、全力で、数値など）は残します。整えたら、原文と整えた文で `revert_broken.py` をもう一度実行し、戻る所が無くなるまで繰り返します。
4. `revert_broken.py` が「残っている候補」を出したときは、原文と読み比べます。「必ず」「のみ」「まで」のような約束の言葉や、否定・条件が消えていたら、同じ意味に見えても原文の言い方に戻します。
5. `yomiyasu_diff.py` の `--stance` には、Step 1 で確かめた主たる立場を指定します。決めきれない場合は省略します。出力された候補（文末の種類が変わった文、言い回しの増減、元にない語、消えた語、箇条書きと段落の変化、つながり）を1つずつ確かめます。候補を理由に、働きの違う文まで同じ文末へそろえません。この検査を受けた修正は1回だけ行い、再実行の往復はしません。
6. `trim_commas.py` は最後に実行します。スピーチや読み上げの原稿には使いません。

### 生成の手順
書いた文を `書いた文.md` に保存し、`yomiyasu_lint.py 書いた文.md` と `trim_commas.py 書いた文.md 読点を直した文.md` を実行します。原文が無いので、比べる3本は使いません。

### 要約・簡潔の手順
`check_meaning.py 原文.md 短くした文.md` と `yomiyasu_diff.py` で、数値と条件が変わっていないかを確かめます。`revert_broken.py` は、削った文を差し戻すので使いません。

## 13. 出力フォーマットと出力の姿勢

推敲を頼まれたときは、次のフォーマットで提示します。意味を確定できない箇所がある場合は「書き直した本文」を「暫定文」とし、本文内でも未確定箇所を示します。本文のみなど出力の指定がある場合は、その指定を優先します。ほかの作業の途中で文を直すときは、最終版だけを使い、点検の結果は報告しません。

```markdown
### 書き直した本文

（書き直した本文。意味が未確定の箇所は、その点が分かる暫定文）

---

### 変えたところ
- （意味が動きやすい変更、つながりを直したところ、文末を立場に合わせてそろえたところ、補ったものだけを、最大5点まで記載。文末をそろえた箇所は1行にまとめて記載。該当がなければ「なし」と1行で記載）
- 元の表現 → 書き直し後の表現（変更理由）

### 残したAIっぽいところ（※意味や重みを担っているため消さずに残した前置きや結びがある場合のみ記載。なければこの見出しごと出さない）
- （残した表現と、意味や重みを保つために残した理由）

### 書き手に確かめたい点（※意味・条件・用途などが不明で、本文を確定するために確認が必要な場合のみ、最大2点まで記載。なければこの見出しごと出さない）
- （未確定の内容と、本文にどう影響するかを短く記載。提供済みの文脈は聞き直さず、意味を保って残せる表現を削るかどうかという好みの問いは出さない）
```

直す所が無くても、原文を「書き直した本文」としてそのまま全部返し、「変えたところ」に「なし」と書きます。「そのまま返して」「一字も変えずに」と言われているときは、原文だけを返します。指摘だけを頼まれたときは書き換えません。

どの依頼でも、次の姿勢で出力します。
- ユーザーへの説明と、ユーザー名義で提出する成果物を混同しません。
- 求められていない「改善しました」「以下に示します」などの前置きや、定型のまとめを付けません。
- 頼まれたものだけを返します。見出しの構成を頼まれたら見出しだけ、訳を頼まれたら訳だけを返します。語法の解説や別案は、頼まれたときだけ付けます。
- 短い会話には短く返します。
- この資料の言葉づかいを、そのまま出力に持ち込みません。出力では、その場で普通に使われている言葉を選びます。
- 絵文字や不要なカッコを、説明や変更理由に使いません。

## 14. 毎回読み込む短い版（ALWAYS.md）

`ALWAYS.md` は、この Skill の要点を普段の返事にも毎回効かせるための短い版です。この SKILL.md は、人に出す文章を書くときと直すときにだけ読み込みます。短い版を使うには、Claude Code の設定ファイル（`~/.claude/CLAUDE.md`、またはプロジェクトの `CLAUDE.md`）に次の1行を足します。登録は利用者が行います。

```
@~/.claude/skills/clear-japanese/ALWAYS.md
```
