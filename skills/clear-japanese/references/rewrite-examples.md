# 直す前と後の例、参考にした研究

この資料の範囲は、`rewrite-rules.md` の決まりごとに対応する、直す前と後の例です。決まりの本文は `rewrite-rules.md` にあり、この資料には書かない。例の候補は、原文と文脈で同じ意味になる場合だけ使う。表の左の列と同じ形の文でも、文脈が違えば直し方は変わる。この資料は yomiyasu（MIT）の構文変換原則を元にしている。

## 動作主・対象・動作を明確にする例

決まりは `rewrite-rules.md` の「主語と目的語の明確化」にある。「XをYとして登録」と「XのYを登録」のように、使う語が同じでも対象が変わる場合がある。仕事の通知を表す「連絡が担当者に飛ぶ」を直す場合は、「担当者に連絡が届く」のように受け手を先に置く案も検討する。

| 確認する表現 | 整理した表現 | 解説 |
|---|---|---|
| 両者を突き合わせることで、差分が浮き彫りになる。 | 両者を比べると、違いがはっきり分かる。 | 元にない名詞を足さず、「浮き彫りになる」の含みを「はっきり分かる」に残す。常体も保つ。 |
| 処理を流すたびに、状態が勝手に書き換わっていく。 | 処理を流すたびに、意図せず状態が書き換わっていく。 | 「勝手に」の不本意な含みを「意図せず」に残す。「流す」の指す処理は文脈なしに限定しない。 |
| 使い倒すことで、道具が手に馴染む。 | 徹底して使い込むことで、道具を思い通りに扱えるようになる。 | 「使い倒す」と「手に馴染む」の含みを平易な言葉で残し、常体も保つ。 |
| 前後を取り違えると、意図しない挙動につながる。 | 前後の順序を間違えると、意図しない動き方につながる。 | 「挙動」を平易にし、原因と結果の関係、常体を保つ。 |

## 文書の立場に文末を合わせる例

決まりは `rewrite-rules.md` の「文書の立場と文末」にある。

| 混在・不自然な表現 | 立場に合わせた表現 | 解説 |
|---|---|---|
| 会議の前に資料を共有しておきます。事前の確認を心がけましょう。（※読み手への助言・心得の文書） | 会議の前に資料を共有しておきましょう。事前の確認を心がけましょう。 | 読み手に勧める文書のため、書き手の方針のような「〜しておきます」を勧めの文末へ統一する。 |
| パスワードは定期的に更新しましょう。安全性を保つことが重要です。（※チームの運用ルールの文書） | パスワードは定期的に更新します。安全性を保つことが重要です。 | 運用ルールの文書のため、勧めの文末を決まりの「〜します」へそろえる。決まりの理由を述べる文（〜ことが重要です）はそのまま残す。 |

## 擬人化を直す例と残す例

決まりは `rewrite-rules.md` の「擬人化の解消」にある。主語が道具や概念であることだけを理由に直さない。

| 確認する表現 | 整理または保持する表現 | 解説 |
|---|---|---|
| このドキュメントが、APIの仕様を語っている。 | このドキュメントにAPIの仕様が書かれている。 | 内容の所在として書き直し、常体を保つ。 |
| 新しいガイドラインが、チームに変化を促す。 | 新しいガイドラインがチームに変化を促す。 | 作用の説明として保持する。実際に変化が進んでいるという出来事へ変えない。 |
| コードが自らの振る舞いを証明する。 | コードが自らの振る舞いを証明する。 | 「証明」が何を指すかを文脈で確かめる。非生物主語だけを理由に「示す」へ弱めない。 |
| 画面の配置が、利用者の迷いを誘う。 | 画面の配置が利用者の迷いを誘う。 | 原因と結果の説明として保持する。配置が分かりにくいという評価や、状況が変化したという情報を足さない。 |

## 比喩動詞をふだんの言葉に直す例

決まりは `rewrite-rules.md` の「比喩動詞の具体化」にある。次の表は、比喩が指す中身が文脈から1つに決まった場合の例である。中身が決まらない場合は、原文の言い方を残す。

| 比喩表現 | 自然で直接的な表現への置き換え | 解説 |
|---|---|---|
| 例外が起きたときは、安全側に倒す。 | 例外が起きたときは、安全を優先する。 | 「倒す」を平易にし、元にない処理内容は補わない。常体も保つ。 |
| この工夫が、後々の運用で地味に効いてくる。 | この工夫が後々の運用で目立たないながらも役立ってくる。 | 「地味に」の含みと、後々役立つようになることを残す。条件や余計な強調語は足さない。 |
| 古いコードの問題を1つずつ潰していく。 | 古いコードの問題を1つずつ直していく。 | 「潰す」を平易な動詞に直し、常体も保つ。 |
| 通信が切れた瞬間に、画面が静かに固まる。 | 通信が切れた瞬間に、気づかないうちに画面が動かなくなる。 | 「静かに」を気づけない幅のまま直し、出来事のタイミングと常体も保つ。 |
| 設定の反映に丸一日溶かしてしまった。 | 設定の反映に丸一日かかってしまった。 | 後悔の含みと常体を残して平易に記述する。 |

## 前置きと否定対比を整える例

決まりは `rewrite-rules.md` の「セルフラベリングと否定対比の整理」にある。

| 不自然な例（前置き・対比） | 自然な表現 | 解説 |
|---|---|---|
| 結論から言うと、このボタンを押すだけで完了します。 | このボタンを押すだけで完了します。 | 単なる前置きは削り、本題から直接書く。 |
| 重要なのは、画面の見た目ではなく裏側のデータ構造です。 | 画面の見た目ではなく、裏側のデータ構造が重要です。 | 評価（重要）を述語に残し、否定対比を保つ（「そのもの」等は足さない）。 |
| 目的は、機能の追加ではなく使いやすさの向上です。 | 機能の追加ではなく、使いやすさを高めることが目的です。 | 否定対比が方針の切り替えを示しているため、否定を残して表現を整える。 |

## ダッシュ記号を置き換える例

決まりは `rewrite-rules.md` の「装飾記号と不要な空白の排除」にある。ダッシュを外して前後を1文につなぐと、前の理由や条件（「〜ため」「〜なら」など）が後ろの部分まで掛かるようになる場合は、2文に分ける。

| 不自然な例（ダッシュ挿入） | 自然な表現 |
|---|---|
| 重要な機能――とりわけ認証周り――は慎重に実装する必要があります。 | 重要な機能、特に認証周りは、慎重に実装する必要があります。 |

## 同じ意味を繰り返すカッコを削る例

必要な情報は地の文に直接組み込み、同じ意味を繰り返すだけの注釈カッコを削る。

| 不自然な例（重複カッコ） | 自然な表現 |
|---|---|
| 修正前のAI生成文（素の出力） | 修正前のAI生成文 |
| 不自然な日本語（いわゆるAI臭さ） | AI特有の不自然な日本語 |

## 和欧文間の不要な半角空白を除く例

日本語の助詞やひらがなとアルファベットの間は、空白を空けずにつなぐ。周りの文書が空白を入れている場合は、その文書に合わせる。Markdownの太字の印の外側に表示のために入れる半角スペースは例外である。

| 不自然な例（不要な空白） | 自然な表現 |
|---|---|
| `この README は、 clear-japanese で 生成させた文章です。` | このREADMEは、clear-japaneseで生成させた文章です。 |

## 段落の話題と文のつながりを整える例

決まりは `rewrite-rules.md` の「段落と文の論理構造（つながり）」にある。次の表には、直す例と、直さずに残す例の両方を載せている。

| 確認する表現 | 整理または保持する表現 | 解説 |
|---|---|---|
| 開発を円滑に進める上で、意識したい点があります。定期的な進捗共有を行うことが推奨されます。 | 開発を円滑に進める上で意識したい点として、定期的な進捗共有を行うことが推奨されます。 | 予告を統合しても、意識したいという重みと、推奨されているという働きを残す。効用の断定へ変えない。 |
| エラー処理を組み込みました。また、通信失敗時にも自動で再試行が行われます。 | エラー処理を組み込みました。また、通信失敗時にも自動で再試行が行われます。 | 実装済みという事実と、処理の動作説明を区別して残す。再試行も今回実装したとは決めない。 |
| 設定を変更しました。ただし、再起動が必要です。 | 設定を変更しました。ただし、再起動が必要です。 | 変更済みという完了事実と、再起動が必要という留保を残す。「ただし」を不要と決めない。 |

次の表は、構造の点検用に作成した例である。修正案は、表に書いた文脈がある場合に限って検討する。

| 原文と提供文脈 | 検討する文 | 保持する関係 |
|---|---|---|
| 処理の実行の完了の確認後に通知を送る。 | 処理の実行が完了したことを確認してから、通知を送る。 | 完了を確認した後に通知する順序。担当者や期限は足さない。 |
| 私は昨日、届いた荷物を開けた。文脈では開けた日が昨日で、到着日は未指定。 | 私は届いた荷物を昨日開けた。 | 昨日は開封日に掛かる。主語と常体は保つ。荷物が届いた日や、今日開けたという情報は足さない。 |
| 通信が切れた場合だけ、再送します。 | 通信が切れた場合だけ、再送します。 | 再送の限定が明確なので残す。「だけ」を落とさない。 |
| 全員が賛成したわけではありません。 | 全員が賛成したわけではありません。 | 全員賛成の否定。全員反対や賛成者の有無を確定しない。 |
| 形式が正しければ取り込み、違っていれば処理を中止して通知します。 | 形式が正しければ取り込み、違っていれば処理を中止して通知します。 | 二つの分岐が追えるので残す。正しい形式の場合にも中止や通知を適用する文へ変えない。 |

## Markdownの太字が表示される書き方の例

直し方の優先順は `rewrite-rules.md` の「装飾記号と不要な空白の排除」にある。

| 表示されない書き方 | 表示される書き方 | 直し方 |
|---|---|---|
| `次に**「文書の立場」**を決めます。` | `次に「**文書の立場**」を決めます。` | かっこの内側だけを太字にする |
| `これは**必須です。**詳しくは下に書きます。` | `これは**必須です**。詳しくは下に書きます。` | 句点を太字の外に出す |
| `立場は**「勧め」か「決まり」**で決めます。` | `立場は **「勧め」か「決まり」** で決めます。` | `**` の外側の文字に接する側に半角スペースを1つ入れる |

太字にならない理由は次のとおりである。GitHub Flavored MarkdownやCommonMarkでは、`**` のすぐ内側が記号（「」『』（）【】、。やバッククォート等）で、すぐ外側が文字（ひらがな・漢字・英数字）である場合、`**` は太字として解釈されず、そのまま文字として表示される。この仕様は、CommonMark Spec 0.31.2（2024-01-28）の6.2節「Emphasis and strong emphasis」にあるleft-flanking / right-flanking delimiter runの定義と、GitHub Flavored Markdown Spec 0.29-gfm（2019-04-06）に基づく。

記号として扱われる範囲は、仕様の版によって違う。[GitHub Flavored Markdown Spec 0.29-gfm](https://github.github.com/gfm/#punctuation-character)は、ASCIIの句読記号とUnicodeのP類（句読点類: Pc、Pd、Pe、Pf、Pi、Po、Ps）を記号として数える。[CommonMark Spec 0.31.2](https://spec.commonmark.org/0.31.2/#unicode-punctuation-character)は、さらにUnicodeのS類（記号類）も記号として数える。そのため、矢印「→」などの非ASCIIのS類に接する太字が、GitHubでも必ず同じ理由で崩れるとは限らない。`scripts/yomiyasu_lint.py` は、GFMとCommonMarkの両方で表示される形を検査している。CommonMarkのフォーラムの「Emphasis and East Asian text」（2017年6月）にも、日本語の `猫は**「のどか」**という。` で太字にならない例がある。

## 参考にした研究と調査

以下の研究や調査を参考に、文章を評価する観点と、このSkillの編集方針を整理した。

### 1. 書式による評価の偏り（Zhang et al., ACL 2025）
[この研究](https://aclanthology.org/2025.acl-long.1308/)では、人間や評価モデルが文章の質とは別に太字・箇条書き・絵文字などの書式を好む偏りを報告している。このSkillでは、装飾の多さと内容の良し悪しを分けて確かめ、装飾を必要な範囲に制限する。

### 2. 日本語の平易化を評価する4基準（Yamashita et al., LREC 2026）
[この研究](https://aclanthology.org/2026.lrec-1.85/)は、「必要性」「十分性」「文レベルの平易さ」「文書レベルの平易さ」の4基準で平易化を評価している。このSkillでは、必要な情報と意味を保ちながら、文単位でも文章全体でも読みやすいかを確かめる。

### 3. 意味の保持と情報の付け足しの防止（Jeong et al., ACL 2026 / Ide et al., 2026）
[Jeong et al.の平易化研究](https://aclanthology.org/2026.acl-long.1086/)と[Ide et al.の辞書定義生成研究](https://arxiv.org/abs/2601.01842)を、意味を保って平易に書く手法の参考にした。このSkillでは、技術的制約・数値・条件分岐を勝手に落とさず、原文にない免責事項や大げさな前置きも足さない。原文の意図と事実関係を保つ。

### 4. 日本語の依頼表現と相手との距離感（Chen et al., Discover Education 2025）
[この研究](https://link.springer.com/article/10.1007/s44217-025-00920-w)は、AIと日本語母語話者の依頼表現を比べ、呼びかけ語や敬語の使い方の違いを報告している。このSkillでは、動作主と文の働きを確かめてから語調を整える。依頼か説明か決まらない場合は、その働きを勝手に決めず、`rewrite-rules.md` の「情報が足りない場合の暫定文」に従う。

### 5. 人とAIの文体の違い（Zaitsu et al., PLOS ONE 2025 / 三浦・久保山, JSAI 2026）
[Zaitsu et al.の研究](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0335369)は、人とAIの文体の違いと、人がAI生成文を見分ける難しさを扱う。[三浦・久保山の研究](https://www.jstage.jst.go.jp/article/pjsai/JSAI2026/0/JSAI2026_5YinA18/_article/-char/ja/)は、生成AIによる文体への影響を扱う。このSkillでは、滑らかに読めることだけで良い改稿と判断せず、各文の働きと書き手の文体を保つ。

### 6. Qiita 7万記事の分析（逆瀬川 2026）
[この調査](https://nyosegawa.com/posts/qiita-writing-before-after-ai/)では、AI普及前後のQiita記事で、太字3倍・箇条書き1.8倍・読点間隔の短縮・ダッシュ記号の10倍増などの変化が報告された。この比較だけで、AIが変化の原因だとは確定しない。このSkillでは、過剰な装飾を減らし、原文から分かる手順や操作を具体的に書く。

### 7. 文の構造とAI特有の言い回しの分析（nasuvitz / ktrmnm 2026）
主語と述語の関係、非生物主語、不自然な比喩、不要な前置きや否定対比を見直す観点を参考にした。主語が道具や概念であることだけで直さず、文脈に合う自然な表現や、意味を担う対比は保つ。
