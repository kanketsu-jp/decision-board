# 検証の記録

> この記録は、clear-japanese が取り込んだ nihongo（MIT、https://github.com/AnIT012/nihongo）の v2.3.1 までの検証の記録です。本文に出てくる「nihongo」「Lite」「Full」は、取り込み元の版を指します。clear-japanese では、Lite は `ALWAYS.md`、Full は `SKILL.md` と `references/` に当たります。yomiyasu と統合した後の clear-japanese では、同じ比較を測り直していません。統合後の版を確かめる時は、`tasks/` の課題をそのまま使えます。

nihongoは、ルールを1つ変えるたびに、変える前の版と目隠しで比べて、良くなった時だけ採用しています。この文書は、その記録です。

## 比べ方

- 同じ原文と依頼を、比べる版ごとに別々のAIに渡して直させます。それぞれのAIは自分の版のスキルしか読めません。
- 出来上がった2つの文をXとYに並べ替え、どちらがどの版かを伏せて判定します。XとYの割り当ては課題ごとにランダムです。
- 判定は、作者が読み比べる方法と、別のAIに判定させる方法の2つを使いました。別のAIに判定させる時は、課題ごとに「変わってはいけない点」の一覧を渡し、1つでも崩れた案は、読みやすくても負けにしています。
- 判定では、次の3つを分けて見ます。
  - 自然さ：読み手、載る場所、文書の役割に合っているか
  - 意味の保持：誰が何をするか、期限、条件、否定、数値、要求の強さ、確かさが変わっていないか
  - 直す深さ：直すべき所を直し、直さなくていい所に手を入れていないか

課題の原文は `tasks/` に置いてあります。どれもAIが書いた合成の文章です。

## 結果

### 推敲の比較（作者が判定）

AIが書いた原文を直す課題で、nihongoと、推敲用に作られた別の公開スキルを比べました。

| 回 | 課題 | nihongoが自然だった数 |
|---|---|---|
| 1 | 新しく書く8題（LINE、ビジネスチャット、謝罪文、技術ドキュメントなど） | 8 / 8 |
| 2 | 直す7題 | 7 / 7 |
| 3 | 意地悪な4題（長文、崩れた原文、5人への書き分け、情報の多いお知らせ） | 4 / 4 |
| 4 | 直す7題（相手のスキルを最新版にして再実施、`tasks/rewrite/`） | 7 / 7 |

### 意味の保持（別のAIが判定）

条件、否定、程度、時系列、対象の範囲、誰が何をするかを、わざと入れた業務文書3題（`tasks/meaning/`）で確認しました。31項目のうち、事実や求める行動が変わった所はありませんでした。

### ルールを足した時の比較（作者が判定）

足そうとしたルールの多くは、変える前の版に勝てませんでした。勝てなかったものは入れていません。

| 足そうとしたルール | 結果（新しい版の勝ち-負け） | 採用 |
|---|---|---|
| 発話意図と文末を保つ | 3-3（1題は同じ文） | しない |
| 上に、文末をそろえてよい場合の補足を足す | 0-4 | しない |
| 2つをまとめた「発話意図と自然さの両立」 | 2-5 | しない |
| 前後のつながりを確かめる | 3-4 | しない |
| 情報の順番とまとまりを確かめる | 3-4 | しない |
| 句点と文章全体のリズム（合成の例文つき） | 5-2 | する |

ルールの文だけを足した版はどれも勝てず、例文を付けた版で初めて勝ちました。

### 技術文書の強化（別のAIが判定）

README、API仕様、障害報告、設計メモ、PR、論文の要旨、運用手順などで、強化前の版と比べました。

- 強化前の版との比較：3回で15勝1敗3分け。意味が崩れたのは強化前の版だけで6回。
- スキルを使わないAIとの比較（最新のv12）：16勝10敗2分け。新しく作った課題だけでは7勝5敗。
- 推敲用に作られた別の公開スキルとの比較：21勝3敗4分け。

- 技術文書以外の7題で強化前の版と比べた回帰テスト：5勝1敗1分けで、悪くなった場面はありませんでした。

- 推敲の最後に原文と照らす手順を足した v14：同じ19題を2回ずつ回して16勝12敗10分け、意味が崩れた数は8から4に減りました。

詳しくは `technical.md` にあります。スキルを使わないAIには、強化した直後の版が一度負けていて、そこから直した経緯も載せています。

### 意味の崩れを戻す手順（1.2.0、別のAIが判定）

推敲で意味が崩れる原因を調べると、文章を丸ごと書き直す時に、予定を言い切りに変える、「大幅に」「全力で」を消す、説明の文を削る、の3つが多いと分かりました。そこで、直した文と原文をスクリプト（clear-japanese では `scripts/revert_broken.py` と `scripts/check_meaning.py`）で比べ、数値・否定・確かさ・強さ・程度の言葉が変わった文だけを原文に戻し、戻した文だけをAIが周りに合わせて整える手順を足しました。

- 推敲用に作られた別の公開スキルとの比較（33題、最初から1.2.0で直したもの）：27勝4敗2分け。意味が崩れたのは1.2.0が5題、相手が3題。
- 同じ19題を2回ずつ回した比較（1.1.0の下書きに戻す手順を当てたもの）：相手に25勝7敗6分け。意味が崩れた数は、1.1.0の8から4に減りました。1.1.0との直接の比較は7勝9敗22分けで、22題は同じかほぼ同じ文でした。
- 試して採用しなかった版：直しを1か所ずつ差し替える版は、崩れは減りましたが、直し方が控えめになりすぎて1.1.0に9勝24敗でした。してはいけない直し方を並べた版と、通して読む工程を足した版は、どちらも1.2.0に負けました（11勝19敗、10勝21敗）。
- 読み手役のAIに1回だけ読ませて、頭に残ったことを2〜3行のメモにさせ、別のAIがメモだけで質問に答えるテストも試しました。原文、1.2.0、相手のスキルの3つで、頭に残った量に大きな差はなく、直した文が原文より多く残るわけでもありませんでした。AIの判定で読みやすいとされることと、頭に残ることは同じではないので、この点は次の課題です。

句点の8題（`tasks/punctuation/`）と長文の6題（`tasks/long/`）も、変わってはいけない点の一覧と一緒に置いています。

### 文と文のつながりとエッセイの骨格（1.3.0、別のAIが判定）

AIの判定役が「読みやすい」と言う文章と、読み手の頭に残る文章が一致しないことが分かったので、読みやすさの研究を調べました。言葉を易しくすると読み手が感じる難しさは下がる一方、実際の理解には文と文のつながりが効いたという研究や、日本語では読み手が知っている情報ほど速く読まれるという読み時間の研究を参考に、つながりの決まりを作りました（参考文献は下に挙げます）。

- 1.2.0との比較（33題を2回、どちらも最初から直したもの）：34勝29敗3分け。意味が崩れた数は1.3.0が5、1.2.0が11。長文の6題は12回中11回で勝ちました。
- 推敲用に作られた別の公開スキルとの比較（33題を2回）：46勝14敗6分け。
- つながりの決まりをすべての文章に当てた版は1.2.0に12勝17敗で、短い文章で負けたため、長い文章だけに当てる形にしました。
- エッセイ6題：話す順番の決まりを足した版は、足す前の版に4勝2敗。字数を埋めるために材料に無い気持ちを足す癖が見つかり、それを止める決まりを足した版は、その前の版に5勝1敗でした。推敲用に作られた別の公開スキルには2勝4敗で、エッセイはまだ弱い分野です。課題は `tasks/essay/` にあります。

参考にした資料：
- 文化審議会「公用文作成の考え方」（2022年）
- Leroy, Kauchak, Mouradi「A user-study measuring the effects of lexical simplification and coherence enhancement on perceived and actual text difficulty」（2013年）
- 浅原正幸「テキストの読みやすさについて」（言語処理学会 第25回年次大会、2019年）
- 吉村伸一「語尾を直しても抜けないAIっぽさ。本当に変えるべきは文章の『骨格』でした。」（note）

### 技術文書の弱点の修正（1.4.0、別のAIが判定）

1.3.0は、宣伝調のPRとREADMEで「飛躍的に」「劇的に」を消したり、「静かに壊れる」（エラーを出さずに壊れる）を別の言い方に変えたりして、意味が崩れることがありました。また、障害の振り返りのような短い技術文書で、見出しで分けずに文章でつなぐ形を選んで負けることがありました。

- 技術文書10題（2回）：推敲用に作られた別の公開スキルに17勝1敗2分け（1.3.0は13勝4敗3分け）。宣伝調のPRとREADMEは4回とも勝ちました。1.3.0との比較は11勝6敗3分けで、意味が崩れた数は1.4.0が1、1.3.0が4。
- 技術文書以外の23題（1回）：1.3.0に12勝10敗1分けで、悪くなった場面はありませんでした。

## 気をつけてほしいこと

- 作者が判定した回は、判定者が1人です。
- 直すAIも判定するAIも、同じ会社のモデル（Claude）を使っています。
- 課題の数は、1回あたり4〜16題です。

## 2.0.0：LiteとFullの2本立て（2026-11-17）

普段の返事にも毎回効かせるため、Fullの要点を約1,100字にまとめたLite（clear-japanese では `ALWAYS.md`）を作りました。課題は [tasks/everyday/](tasks/everyday/) の15題です。雑談、LINE、短い質問、お礼のメール、自己PR、UIの文言、お知らせを入れました。

書く役はすべて同じモデルで、条件だけを変えています。判定は別のモデルに、どれがどの条件か伏せて3つを順位づけさせました。

| 比べたもの | 結果 |
|---|---|
| Lite 対 推敲用に作られた別のスキル | 13勝2敗 |
| Full 対 推敲用に作られた別のスキル | 12勝3敗 |
| Lite 対 Full | 8勝7敗 |

依頼に無い理由・感想・約束などを足した作り話も、別の判定役に数えさせました。15題の合計で、LiteとFullが3件ずつ、別のスキルが9件でした。作り話が起きやすい11題では、スキルを使わない場合に33件ありました。

普段の返事1回あたり、スキル無しより増えたトークンは、Liteが約1,000、Fullを毎回読ませた場合が約9,000、別のスキルが約11,500でした（作業環境の使用量の表示で測った目安）。

Liteは6回作り直しました。2回目から4回目は、長さと口調の決まりを足してもFullとの差が縮まらず、5回目と6回目で作り話を防ぐ決まりを強めました。Fullの原則4にも同じ決まりを足しています。

判定はすべてAIで、課題も15題だけなので、数字は目安です。

## 2.2.0：LiteとFullの役割の分け直し（2026-11-18）

設定なし、プロフィールで口調などを指定した場合、`personal-profile.md` に書き込んだ場合の3つで、新しい10題を書かせました（書き手はClaude Sonnet 5.5、1回ずつ）。

- プロフィールの指定（です・ます、最初に結論を1行、具体例、絵文字なし）は守られました。
- `personal-profile.md` に書いた一人称（僕）が、作文でも使われました。
- 依頼に無い事実を足した作り話はありませんでした。

### 推敲用に作られた別のスキル（最新版）との比較

同じ10題を書かせ、判定は別のAI（Claude Opus 5.5）が目隠しで、順番を入れ替えて2回ずつ行いました。審査の基準は、依頼文だけから作った「入れてほしいこと・要らないこと」の一覧です。依頼どおりか（頼んだ中身と量がそろい、本人の経験や約束を作っていないか）を最優先にし、次にそのまま使えるか、最後に自然さの順で見ました。

| 見た点 | 1回目（20判定） | 2回目（20判定） |
|---|---|---|
| 依頼どおりか（Lite） | nihongo 8、別のスキル 4、引き分け 8 | nihongo 9、別のスキル 4、引き分け 7 |
| 依頼どおりか（Full） | nihongo 10、別のスキル 4、引き分け 6 | nihongo 7、別のスキル 5、引き分け 8 |
| 自然さ（Lite） | nihongo 8、別のスキル 9、引き分け 3 | nihongo 5、別のスキル 10、引き分け 5 |
| 自然さ（Full） | nihongo 6、別のスキル 9、引き分け 5 | nihongo 7、別のスキル 10、引き分け 3 |

- 依頼に無い事実（本人の経験、相手の努力、約束など）を作ったのは、別のスキルだけでした。
- 自然さで負けた理由で一番多かったのは、別のスキルが細部を作って文を生き生きさせた題でした。次がキャッチコピーの勢いの弱さで、これは次の課題です。
- 10題を書いた時に増えたトークンは、Fullが約1.9万、別のスキルが約4.1万でした。

## 2.3.0：書き方メモ

書き方の違う架空の3人（関西弁でwが多い人、絵文字が多い人、絵文字を使わず目上にとても硬い人）を作り、それぞれの文6通から書き方メモを作りました。同じ3人がAIに頼む文を3つずつ、メモありとメモなし（どちらもLite入り）で書き、本人が自分で書いた文と比べて、どちらが本人の文として通るかを目隠しで判定しました。

| 回 | メモありの勝ち | 作り話 |
|---|---|---|
| 1回目 | 9題中8題 | メモあり2件、メモなし1件 |
| 2回目（直した後） | 9題中8題 | 0件 |

1回目で見つかった問題は2つでした。メモの「お疲れさまですで始める」という説明がそのまま文に入ったこと（「お疲れさまですで失礼します」）と、口ぐせの「ほんとに助かる」を入れるために気持ちを足したことです。言葉の例は「」で囲んで説明の文に溶かさないこと、口ぐせのために中身を足さないことを決まりに足しました。人物と判定はどちらもClaudeなので、数字は目安です。
